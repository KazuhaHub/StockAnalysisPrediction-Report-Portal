# v2026.38.3 — the version a page is running, and an update prompt that means what it says

The fourth artifact set of week 38, and the first to carry the work below: **v2026.38.2 built
nothing.** Its six platform builds all failed on a defect in this release's own note packaging —
the pipeline copied the note over a tracked file, which dirtied the worktree, which made `go build`
stamp the binary `vcs.modified=true`, which the artifact check refuses. The tag stands as the record
of that attempt; no archive, image or draft release was ever produced from it.

A reader now sees which build their page is *running*, rather than whichever build the server
happened to answer with first, and the portal can say what a deploy means for them — a new version, a
rebuild of the one they have, a rollback — before they decide to reload.

## Compatibility

Unchanged from v2026.38. **This release requires the v0.4.72 database schema** and, like the two
that shipped, converts nothing: no DDL, no backfill, no stamping. The update policy is a `meta` row like
every other site setting, so no table and no column is added, and a database that v2026.38.1 started
starts here unchanged. Rollback to v2026.38.1 is clean.

## Added

### A localized version label, in the footer and the console

The portal footer and the management rail show the product version — `Version: 2026.38` /
`版本：2026.38`, the CalVer number without the git tag's leading `v`, behind a translated prefix. It
is a button, not decoration: clicking it opens that build's release notes, and hovering or focusing it
reveals the commit and the build time **with the zone it is shown in**, because a bare timestamp reads
as two different dates to the maintainer and the reader.

`footerShowVersion` still hides the footer's copy. It does not disable update detection or the
administrator's policy.

### A release-notes dialog

Release notes are shown in a modal everywhere — never a drawer — following the run manager's dialog:
the same 980px desktop width, mask, header and responsive rules, so the portal keeps one idea of what
a working dialog looks like. The body is the committed note rendered through the existing safe
Markdown path; `View on GitHub` sits on the left and links to the published release page for the full
body, including the generated pull-request list this copy does not carry.

### The administrator decides how hard the prompt insists

One setting, under **Site settings → Update notifications**:

| Policy | What a reader gets |
| --- | --- |
| `dismissible` (default) | A banner with Refresh, View release notes, and Later. Later hides *this* target for this tab session; a different build prompts again. |
| `persistent` | The banner, with no way to hide it. The page stays usable. |
| `required` | The release-notes dialog, opened automatically, with no close button, no Escape and no mask dismissal. |

It is one enum rather than two switches, because "may the reader defer" and "must they refresh" are
one decision read two ways and two booleans can describe a state nobody chose. An unknown value is
refused at the write, and an absent or unreadable stored value degrades to `dismissible` — a corrupt
row must not start blocking every reader.

The policy is published through `/api/version`, so the poll that already tells an open tab a deploy
landed also tells it how hard the portal is insisting: escalating to `required` reaches a tab nobody
has reloaded, and relaxing it unblocks a required dialog that is already on screen. Applying it to
both the portal and the console is structural — one coordinator owns the state and renders the dialog
once, so there is no second overlay to stack.

**Nothing refreshes the page for anyone.** Required mode is a browser interaction policy, not a
security guarantee: it does not install software, upgrade a database, or block an old API client. The
refresh is always the reader's click, and the dialog warns that unsaved work goes with the page.

## Changed

### The page's build identity is compiled in, not inferred

The footer used to show whatever `/api/version` answered first. That describes the *server*, and
labelling it "the page you are on" is a claim about a document the browser may have loaded hours
earlier and, under a service worker, from a cache the server no longer serves. The bundle now carries
its own tag, commit and build date, inlined at build time and derived from the same tuple the binary
is stamped with, so "this page is not the build the server is serving" is an equality check rather
than a guess. When the identity cannot be established the label says so; it never substitutes the
server's.

`/api/version` keeps its existing fields unchanged and gains `updatePromptPolicy`. Additive for every
consumer.

### What the prompt says

| Situation | Wording |
| --- | --- |
| A numerically newer version | `New version 2026.38.3 is ready.` |
| The same version, a different build | `Page update available.` |
| A lower version | `Server version changed. Refresh to switch to 2026.38.` — never described as a new release |
| A waiting service worker, no confirmed server target | `Page update available.`, and no version is inferred from the worker alone |

Comparison is numeric on `(YYYY, W, R)`, never lexical — `v2026.9` is older than `v2026.10`, and a
week has no leading zero, so a prefix test would be wrong for a third of the year. The ordering only
ever decides *wording*; whether a refresh is needed is the full identity, because a rebuild of the
same number needs it just as much as a new number does.

The target is re-evaluated on every poll while the prompt is open, in both directions: a second deploy
re-points the same dialog at the new build, and a rollback onto the running build clears the prompt.
Failures fabricate nothing — offline or an ended session leaves the update state exactly as it was.

## Fixed

- **The refresh action could fire twice in development.** The duplicate-click guard was a side effect
  inside a React state updater, which `StrictMode` double-invokes in development: two `SKIP_WAITING`
  posts and two reload listeners for one click. It is a ref now.
- **The version tooltip was hover-only.** Details reachable by hovering a span are unreachable by
  keyboard; the tooltip now opens on focus too.
- **The footer version waited on the server.** A portal whose `/api/version` failed showed no version
  at all. The label no longer depends on that request.

## The release path

Two things now travel with a release that did not before, and both are checked:

- **The release note is compiled into the binary.** `docs/releases/<YYYY>/<tag>.md` is copied to
  `internal/version/notes/release.md` before `go build`, where a `go:embed` carries it into the
  artifact, and `GET /api/release-notes` serves it to the dialog. The endpoint matches the requested
  tag **verbatim**, so a neighbouring number can never be answered with this build's note; when the
  note is not this build's, it answers "unavailable" and hands over that tag's exact release link.
- **The injected note lives at a gitignored path**, which is not a detail — it is the fix for this
  release's predecessor. `go build` stamps a binary built from a dirty worktree with
  `vcs.modified=true`, and `scripts/check-release-build.sh` refuses exactly that, because a binary
  that cannot say which revision it came from cleanly is a binary users cannot verify. An injected
  build input therefore has to live somewhere git does not track, the same rule `internal/web/dist`
  has always followed. The committed `notes/placeholder.md` next to it exists only so the embed
  pattern always matches and a fresh clone compiles; it is never served.
- **A release without its note fails before anything is built.** The setup job refuses a tag whose
  committed note is missing, and `check-release-build.sh` searches each built binary for the note
  itself — so a placeholder, or another release's note, cannot ship silently.
- One build date and one short sha are computed once and shared by the SPA bundle and all six
  binaries. Reading the clock per platform would have stamped the page and the binary it ships in
  with different timestamps, and a page would then never recognise itself in the server's answer.

## Rollback

Restore the **v2026.38.1** binary or image. No database, configuration or key-material step is
involved in either direction.
