> 核对日期：2026-10-29，America/Los_Angeles。
> 面向接手开发者：按顺序执行；不要因为看到某个测试通过，就跳过后面的集成步骤。

## 0. 先读这两分钟

### 0.1 最终要做成什么

用户打开应用市场，查看应用，确认权限，点击安装，然后直接打开使用。
静态应用不需要后端；需要后端的应用由平台自动安装、启动、配对和管理。
用户不应手工运行 Docker、填写内部服务地址、复制配对 Key 或 SSH 修复应用。

界面必须像 Portal 自己的页面：统一 React、TypeScript、Ant Design 和共享 SDK；
跟随 Portal 的语言、主题、时区；只有一个标题区；没有套在外面的应用大框；
深色刷新不闪白；返回、前进、链接和未保存表单都正常。

平台管理员可以一次性准备运行环境。这个基础设施步骤与“每安装一个应用手工部署后端”不同。
共享 Linux Docker 运行环境可以管理多个应用容器；不是要求所有应用挤进同一个业务容器。
应用用户不能接触 Docker 控制权限，静态应用也不能被强制依赖 Docker。

### 0.2 当前最容易误解的事实

1. **还没有完成整个平台。** 大量底层组件和隔离测试已完成，但完整用户流程尚未交付。
2. **候选代码不等于 main，也不等于已上线。** 此次快照中，候选基线的依赖链有 131 个仍开放的 PR，末端基于 main。不要只合并最后一个 PR。
3. **命令存在不代表服务已完成。** `cmd/app-runner/main.go` 当前只提供 `inspect-daemon`，不是常驻运行服务；检查成功时 `execution_ready` 仍为 false。
4. **SDK 网络通道有 WIP。** 已保存部分编解码和消息通道；尚未接到 React Hook、宿主页、launch 元数据和真实浏览器链路。
5. **生产权限没有批准。** 已批准的是开发及一次性隔离验收。不能据此部署生产、导入真实 Key、迁移 Status 或发布正式市场包。
6. **服务器版本配置保持 beta。** 不得为方便测试改成固定版本、固定标签或固定摘要。摘要可以用于验收记录，不应擅自替换服务器的版本配置。
7. **新增数据库结构要先确认。** 已批准的具体范围见第 3 节；任务表、事件表、业务存储等不能随手加。

### 0.3 本手册怎么用

- 第 1–4 节：找到正确代码，理解已经有什么、还缺什么。
- 第 5 节：按 H00–H18 开发；每项都有步骤、文件入口和完成条件。
- 第 6–8 节：运行验证、处理失败、完成发布交接。
- [90 项验收清单](handoff/acceptance-checklist.csv)：逐行填实际证据，不是已通过清单。
- [源码与 PR 快照](handoff/source-and-pr-snapshot.json)：精确版本、PR 依赖、核对时的 CI 状态。

[生命周期](03-lifecycle.md)、[P00–P14 工作包](04-implementation.md)、

### 1.5 PR 依赖怎么处理

`handoff/source-and-pr-snapshot.json` 的 `pr_chain_newest_first` 是“从新到旧”，不是合并顺序。
每项的 `headRefName` 是它自己的分支，`baseRefName` 是它依赖的分支。

接手者先做：

1. 确认基线提交确实包含预期文件：`git log -5 --oneline`、`git show --stat <提交>`。
2. 从快照最旧一项开始理解依赖；不要对 131 个 PR 批量执行自动合并。
3. 由熟悉仓库的人决定逐层合并，还是建立独立的整合 PR。
4. 整合时必须同时包含最新 main 的有效修改；不能为了通过测试把 main 的功能覆盖掉。
5. 冲突特别检查迁移编号、基线、通知、权限、恢复、路由和依赖锁文件。
6. 整合后的新 SHA 重新跑完整 CI。原分支绿色不能证明整合版本绿色。
7. 不 force-push 共享历史，不改旧提交归属，不往提交或文档加入工具归属说明。

若选择整合分支，下面仅建立开发候选，**不会发布**：

```sh
git fetch origin
git switch -c kazuha/app-platform-integration origin/main
git merge --no-ff origin/kazuha/app-network-http-gateway
```

有冲突就停止继续提交，逐项核对；不会处理时请审查者处理，不要一律选一边。

## 3. 已批准什么，哪些事情必须先确认

### 3.1 已批准的开发范围

1. Portal 原数据库增加 14 个应用平台控制表；运行环境共享一个 SQLite 日志、4 个表。
   具体结构见 [13](13-control-storage-spec.md)、实现见 [14](14-control-storage-implementation.md)。
2. 共享 Linux Docker 运行环境、Ed25519 包签名、发布者白名单、默认拒绝的能力代理；只限开发与隔离验收。
   见 [18](18-runtime-and-trust-proposal.md)。
3. 凭据扩展方案 A：Portal 原数据库两张表，分别管理加密凭据和应用使用绑定。
   复用已有密钥体系；卸载撤销绑定；恢复暂停并保留撤销记录。
   见 [131](131-secret-binding-storage-proposal.md)、[136](136-credential-schema-and-custody.md)。
4. 现在可以继续上述范围内的代码和假数据测试；不需要重新询问同一项已批准原则。

### 3.2 尚需具体决策的范围

- 业务记录、文件元数据、资源授权的物理表/列/索引/删除及恢复规则。
- 任务、事件、通知意向等后续持久化产品。
- 未覆盖的新部署权限、正式 SDK/API 冻结与正式发布信任策略。
- D5 整体视觉/交互验收，D6 正式发布/生产启用。
- Status 等旧应用逐个迁移、真实凭据使用、具体 OU/余额范围和通知启用。

需要新增结构时，先提交一份具体方案，至少写：表名、每列类型/空值/默认值、约束、索引、
外键、唯一性、上限、并发规则、账号/应用删除、备份导出、旧备份恢复、新旧版本兼容、
恢复后暂停什么、如何保留撤销下限。由负责人确认后再写迁移。

**不能用这些办法绕过确认：** 往 `meta` 塞一批新实体、往策略 JSON 藏业务数据库、
新建未经纳管的 JSON/SQLite 文件、把应用所有数据塞到一个无限大的 blob。

### 3.3 数据库修改的固定步骤

1. 读 ADR 0034、0035、0038、0040 及受影响功能 ADR。
2. 检查当前 main 与工作分支的 `internal/app/migrate_steps.go`，决定下一个未使用编号。
3. 不编辑已发布迁移，不修改 v0.4.72 冻结基线。
4. 同时写 SQLite/PostgreSQL 产品验证与迁移测试。
5. 同时修改备份纳管、恢复顺序、旧备份规则、删除和容量规则。
6. 测试事务中途失败/回滚、并发、重复执行、损坏产品、缺失密钥、旧备份恢复。
7. 恢复之后先暂停执行/投递，再比对实际进程，不能默认旧进程已经停止。
8. 记录新结构审批与对应测试，审核后才能进入下一项依赖任务。

4. 检查 backend 与 network 两类请求的 ID/取消不会串台；分别限制或明确共同的总上限。

7. 新适配器只能调用当前安装的 `/network` 路由；请求体中的 binding 来自宿主页，不来自应用。
8. 响应流先限原始字节数、严格 UTF-8/JSON 解析，再检查封闭响应结构；不能无限 `response.text()`。
9. 远端 status 401 是响应封套里的业务状态，不应触发 Portal 退出登录。
10. fetch 开始后断线、取消或不认识的响应一律按“不确定”处理；不能自动重试，也不能把远端错误正文暴露为平台错误。
11. 补 launch 能力提示。`app_platform_http.go` 当前仍返回空能力数组；

12. 在 `AppFrameV2.tsx` 接入网络回调；能力/绑定变化必须换掉旧文档/通道，旧请求不能继续控制宿主。

    页面卸载或 presentation 失效后，旧闭包必须拒绝请求。
15. 将网络源文件及测试纳入 `scripts/generate_app_contract.py` 的复制和摘要校验。

17. 更新 Apps 的 SDK 使用说明、模板和标准；业务应用不应自行实现握手、Base64 或 fetch。
18. 新增真实浏览器场景，经 AppRoot/MessagePort/宿主 fetch/会话 HTTP/root/HTTPS 调用。

测试至少覆盖：成功二进制结果、空响应、401 远端业务状态、缺权限、改 OU/撤会话、
页面旧版本、取消、断线不重试、错误字段、1 MiB 响应边界、深色/语言变化不重复提交。

### H06：完成凭据绑定、私有使用与轮换

**对应 P07；已有两表不等于这个任务完成。**

11. 用临时假 Key 做 header 接收测试、轮换中请求、撤销后请求、恢复旧数据、日志/备份/错误检查。

**完成条件：** 假 Key 只到指定测试服务；浏览器、应用常规响应、日志都看不到；旧授权不能继续用新 Key。

**完成条件：** 从干净测试环境按教程能安装、编辑、保存、刷新读取、卸载/重装；不需要应用专属宿主代码。

### H13：完成升级、禁用、卸载、保留数据与恢复闭环

**对应 P10。已有部分 review/removal/恢复底层库，要复用而不是重写。**

1. 先制作一张“动作→当前状态→审核内容→持久化边界→物理动作→确认/不确定→恢复”表。
2. 审查所有仅支持 generation 1 的读写路径，例如当前 `withPlatformBackendRead` 与请求绑定。
   支持升级不能只全局替换字符串 `1`，必须校验新旧 release/权限/数据/进程的完整关联。
3. 普通升级保留 installation ID；新 code/data/权限/配对元组必须整体激活。
4. 更新审核展示权限差异；用户拒绝新增必需权限时旧版本继续可用，不提前改 live grants。
5. 数据迁移前取得一致性恢复点，阻止旧 writer；运行明确声明的迁移，不允许任意宿主脚本。
6. 迁移中断或确认丢失时先查实际结果；不能盲目重跑，也不能拿旧代码读不兼容数据。
7. 新版就绪失败：只在读写兼容或已验证恢复数据后回退；不能只把镜像标签改回去。
8. 新版已写入后再回退，明确告知恢复点与可能丢失的数据，按确认流程处理。
9. 禁用先阻断新请求/任务认领；runner 不在线时 UI 显示停止待确认，不能谎称已停进程。
10. 启用/修复重新核对信任、当前授权和真实健康，不偷偷新增能力。
11. 卸载撤销所有运行/任务/订阅/通知发布/凭据使用；保留数据默认不删除。
12. 保留数据重装使用显式兼容性和身份审核；不自动沿用旧 app-use 或 secret grants。
13. 永久删除数据单独确认版本与范围，处理并发旧请求和恢复副本，不能按名字删除不明容器/目录。
14. 备份把 Portal 控制、共享 journal、应用数据、代码身份和密钥关联到同一恢复点。
15. 恢复到隔离新环境，外部执行/投递保持暂停；比对真实进程和 epoch，再由管理者复核。

至少实际注入：下载中断、写入后丢确认、启动后丢确认、迁移一半失败、迁移完成丢确认、
健康失败、runner 离线、两个操作者冲突、恢复旧 Portal 而 runner 更新、密钥缺失。

**完成条件：** LIFE-06..15、DATA-04..08、OPS-01/06 的完整闭环有证据，不仅正常升级能跑。

## 6. 每次提交前应该怎么验证

### 6.1 Portal 前端

在 Portal 根目录：

```sh
npm --prefix web run lint
npm --prefix web run typecheck
npm --prefix web test
npm --prefix web run build
```

预期每条退出码为 0。测试 PASS 但 typecheck 失败仍不通过。
构建完再进行需要嵌入 `web/dist` 的 Go 构建；不要两者并行改同一目录。

### 6.2 Portal 后端聚焦检查

普通网络/HTTP：

```sh
GOWORK=off GOTOOLCHAIN=go1.26.10 GOMAXPROCS=2 go test -race -p 2 ./internal/app -run '^TestPlatformNetwork(Request|HTTP)'
```

凭据/策略/卸载撤销：

```sh
GOWORK=off GOTOOLCHAIN=go1.26.10 GOMAXPROCS=2 go test -race -p 2 ./internal/app -run '^TestPlatform(Credential|SecretBindingPolicy|SecretUninstall)'
```

网络底层包：

```sh
GOWORK=off GOTOOLCHAIN=go1.26.10 GOMAXPROCS=2 go test -race -p 2 ./internal/apprunner/broker ./internal/apprunner/control ./internal/apprunner/transport ./internal/appplatform
```

对应功能变化时再补它的专门用例。用 `rg -n '^func Test' 文件名` 查真实名称，
不要把验收编号 `AUTH-01` 直接当 `go test -run` 名称。

### 6.3 Portal 与 SDK 共享源检查

下面例子假定使用 1.4 节的两个相邻目录，命令从 Portal 根目录运行：

```sh
python3 scripts/generate_app_contract.py --apps-dir ../Portal-Apps-v2-work
python3 scripts/generate_app_contract.py --check --apps-dir ../Portal-Apps-v2-work
```

第一条会更新生成产品，必须审查两个仓库的 diff；第二条应无漂移报错。
H02 还要把新 network 文件纳入生成器；当前脚本只检查到的既有产品不能证明所有新文件都已纳管。
生成后两边都提交，记录互相对应的 SHA；不能只改 SDK 一份。

### 6.4 Apps 仓库

```sh
python3 scripts/plugin-standard.py
npm run typecheck
npm run test:sdk
python3 scripts/test-app-template.py
python3 -m unittest discover -s scripts/tests -v
```

应用自己有额外测试/构建时，一起运行；共享 SDK 改动要验证受影响应用。
不能修改测试的预期来掩盖行为退化，不能把失败的 consumer 从 workspace 中移除。

### 6.5 Linux 原生与浏览器 CI

使用已有 PR 工作流，不把 root 夹具拿到生产或个人常用 Linux 主机上运行。
不要手工伪造 `GITHUB_ACTIONS=true` 等环境变量来跳过隔离前提。

先提交开发分支并创建 PR，然后查看：

```sh
gh pr checks <PR编号>
gh run list --branch <你的分支名> --limit 10
gh run view <运行编号>
```

上面的尖括号是占位符，换成实际编号/分支；不要原样执行。
查看特定失败日志：

```sh
gh run view <运行编号> --log-failed
```

判断规则：

1. 先核对该 run 的 `headSha` 是正在验收的提交。
2. 工作流 queued/in_progress 就是还在执行，不要误判为死掉并重新提交触发取消。
3. 一次查询超时不等于执行失败；继续查看同一个 run/job。
4. SKIPPED 与 PASS 不同；检查必需场景为什么跳过。
5. 真实 PostgreSQL 组必须有临时 DSN，并真的执行 Postgres 用例。
6. quota 报告中的标记由断言成功后产生；源码里出现标记不等于执行过。
7. 完整普通 Go 测试不能因为聚焦测试绿色而删除。
8. 文档证据更新不要反复推送到正在长跑的功能 PR，让 CI 无谓取消。

现有完整测试可能运行较久，候选配置 `go-test` 总超时为 35 分钟。
时间变长先看具体步骤与资源，不要为“更快绿”删除测试、跳过漏洞检查或放宽安全策略。

### 6.6 成功/失败/不确定三种结果要分清

| 结果 | 给用户的含义 | 程序怎么做 |
| --- | --- | --- |
| 确定成功 | 结果被确认 | 更新界面一次；记录对应版本/操作身份 |
| 确定拒绝/尚未执行 | 权限/兼容/输入问题 | 展示明确安全原因；满足条件后由用户重新操作 |
| 不确定 | 可能已执行但未确认 | 不返回未经授权的敏感结果；不自动重试；查记录/外部效果后复核 |

不要把“不确定”包装成普通网络失败后直接重发。这可能重复写数据、发消息或产生费用。

## 7. 常见卡点及处理顺序

### 7.1 类型检查失败但测试通过

先看报错文件。测试运行器通常只转译，不代表 TypeScript 类型正确。
用库当前支持的 API，不为一个 `Object.hasOwn` 直接升级整个项目 target。
mock 函数应声明真实参数，避免无参 mock 的空 tuple 被当有参调用。

### 7.2 共享 SDK 校验摘要不一致

确认改的是 Portal 源文件，再用生成器同步到 Apps；检查每个新模块是否进入生成与校验清单。
不要手工伪造一个摘要让检查通过，也不要关掉漂移测试。

### 7.3 iframe 空白、协议不兼容或主题闪白

1. 确认实际 frontend ZIP/entry/digest 与当前 launch 一致。
2. 检查 CSP、脚本本地资源和握手；版本/字段不匹配要修两边。
3. 检查 initial presentation 前是否暴露内容、loading 遮罩是否与主题同色。
4. 用浏览器工具取错误；不要靠删除 sandbox/CSP 解决。
5. 不要为某个应用单独写 host DOM 注入补丁。

### 7.4 managed 安装一直没有就绪

依次查：当前权限/计划→runner 兼容→journal→准确的原生进程身份→实际数据/IPC 挂载→
应用是否监听私有 socket→就绪协议→配对/boot→Portal 原子激活。

#354 曾遇到的问题是 root 测试和 Docker daemon 的 mount namespace 不一致，
新建 IPC tmpfs 对 daemon 不可见。正确修复是保持所需挂载可见性，网络单独隔离。
不能因为等不到就绪而跳过就绪、扩大权限或直接写 ready 字段。

### 7.5 旧 fixture 间歇“阶段证据不匹配”

记录精确用例、源 SHA、数据库驱动、时序与首个错误；区分 fixture 构造失败还是产品拒绝。
检查数据库时钟/记录顺序/租约/历史摘要等实际条件，再决定修复。
复跑只用于定位，不把“最终碰巧绿”写成根因已解决。

### 7.6 变更后出现 U1000/静态检查失败

确认完整路径真的由产品或有意义的测试使用。不要加空调用或禁用检查掩盖未接线。
当前网络协调器曾因为没有测试调用完整 dispatch 路径报 U1000；修正是增加真实拒绝路径测试。

### 7.7 PR 绿色但合到 main 后坏了

原 PR 的绿色只对当时 head 和 base 有效。重新检查整合后的迁移、lockfile、生成产品和权限路径，
在整合 SHA 上重新运行完整 CI。不要改生产环境去迁就分支代码。

### 8.2 “这一项完成”的判断

只有下面都满足才把任务标为完成：

- 该项要求真的在产品路径中，而不只是测试工厂或一个私有函数。
- 有正常路径，也有拒绝/并发/失败/恢复中必要的反例。
- 数据、权限、生命周期、SDK/页面和文档同时更新。
- 验证使用精确当前 SHA；没有把未跑/跳过/历史版本的结果算进去。
- 没有留下必须靠开发者 SSH、改库、改配置才能让应用用户继续的隐藏步骤。
- 对应验收编号有足够范围的证据。
